# Migration to Research OS v1.4.0

Research OS v1.4.0 moves execution policy to one canonical runtime while preserving the research-safety invariants established in v1.2.x. This is an architecture/API migration, not a database-schema migration.

## 1. Database migration

No new Alembic migration is required for v1.4.0. The reversible v1.2 Evidence-lineage migration remains the current schema baseline. Existing historical snapshots and release tags remain immutable.

## 2. Canonical execution path

The supported execution flow is now:

```text
ResearchContext + ResearchInputs
        ↓
ResearchRuntimeFactory
        ↓
ResearchRuntime
        ↓
ResearchEngine + run-scoped PluginRegistry
        ↓
ResearchRunResult
```

`ResearchRuntime` owns composition policy, completion evaluation, component fingerprinting, and snapshot freezing. `ResearchEngine` only executes a capability dependency graph and remains unaware of industries, company identifiers, or plugin identities.

## 3. Removed duplicate policy surfaces

The legacy `src/research_os/orchestration.py` entry point has been removed. The second KPI registry/facade has also been removed. Do not restore either compatibility surface as a new policy source.

Callers should migrate to `ResearchRuntimeFactory.default()` or `ResearchRuntimeFactory.with_providers(...)` and consume `ResearchRunResult`.

## 4. Canonical inputs

Run-specific optional research inputs are represented by `ResearchInputs`. Missing inputs remain missing; callers should not synthesize zeroes, placeholder expectations, or fake valuation execution solely to make a run appear complete.

PIT, evidence-lineage, period, missing-value, KPI-applicability, funding-loop, and completion semantics remain enforced by the pinned runtime.

## 5. Canonical result and reporting

`ResearchRunResult` is the public result boundary. It carries the routed business model, strategy resolution, module results, canonical artifacts, completion result, component fingerprints, and frozen snapshot.

`DecisionSummaryBuilder` consumes `ResearchRunResult` directly. Reporting must obtain `final_status`, `blocking_modules`, and `module_statuses` from the same `ResearchCompletionResult` produced by the runtime. A parallel reporting dictionary or report-local status override is no longer a supported completion surface.

## 6. Plugin migration and extension

Industry and methodology strategy are represented as versioned plugins with a `PluginManifest`. External extensions should be supplied through a `PluginProvider`:

```python
runtime = ResearchRuntimeFactory.with_providers(MyProvider())
result = runtime.run_context(context, inputs)
```

The registry is rebuilt for every run. Plugin registration must therefore be explicit through providers rather than import-time mutation of a process-global registry.

See `docs/architecture/plugin-authoring-v1.md` for the Core API `1.0` authoring contract.

## 7. Business-model coverage

Normal research does not require the caller to choose an industry plugin. The Business Model Router produces a profile and `StrategyResolver` selects compatible eligible plugins. If no compatible strategy exists, the result contains an explicit `CoverageGap`.

A coverage gap is not equivalent to a generic KPI PASS and must not be silently converted into COMPLETE.

## 8. Core API compatibility

Research OS v1.4.0 keeps:

```text
CORE_API_VERSION = 1.0
```

Plugin compatibility is validated independently from the Research OS package version. A plugin declares `api_version`, `min_research_os_version`, and optional `max_research_os_version`; incompatible plugins fail registration instead of being silently accepted.

## 9. Snapshot reproducibility

Snapshots now include component fingerprints for resolved modules/plugins in addition to the existing version bundle and payload hash. Repeated equivalent synthetic runs must remain deterministic. New providers or plugins must preserve auditable version identity.

## 10. Release verification

v1.4.0 adds architecture-first release validation covering runtime contracts, dependency resolution, plugin contracts, compatibility/resolution, coverage gaps, failure isolation, knowledge PIT behavior, canonical result/reporting, component fingerprints, extensibility without engine changes, and absence of the legacy runtime policy surface.

CI order is:

```text
architecture contracts
→ correctness regressions
→ storage migration smoke
→ full test suite
→ release gate
```

The release script retains its historical filename `scripts/release_gate_v1_1.py`, but it evaluates the current package version and the current complete gate set.

## 11. Compatibility notes

- Existing research-domain algorithms, PIT evidence semantics, and v1.2.1 correctness rules are preserved.
- `DecisionStateRecord` adds optional decision-context fields so canonical reporting can remain self-contained; older records without those optional fields remain parseable.
- Reporting code that directly passes an arbitrary dictionary to `DecisionSummaryBuilder.build()` must migrate to `ResearchRunResult`.
- Code importing the deleted legacy orchestrator or the deleted duplicate KPI registry must migrate to the canonical runtime/plugin registry.
- No company-specific production logic or company-specific golden financial fixtures are introduced by this migration.
